# Get-R-Done sample

Get-R-Done (`GetRDone`) is a sample appraisal-management (AMC) application built on Continuum. Its domain is being added from the event model.

## Run

Requires Docker. From this folder:

```
dotnet run --project src/GetRDone.AppHost
```

Open the Aspire dashboard, then the `web` endpoint.

KurrentDB (the events), Azurite (the document files) and SQL Server (the Identity users) keep their data in Docker volumes, so orders and users survive AppHost restarts. The projections are rebuilt from the events when the silo starts, and the seeded lookups are seeded again. To start over, stop the AppHost and delete the volumes (`docker volume ls`; their names end in `-kurrentdb-data`, `-storage-data` and `-sql-data`). Delete the KurrentDB and Azurite volumes together, since orders point to their files. After a change to what an aggregate stores, delete the KurrentDB volume if the old events no longer load. Each run uses a new Orleans cluster ID, so a silo never waits on the previous run's silos in the persisted clustering table.

Demo users (Development only, password `Pass123$`): `ana.ruiz@carterbank.example` (client user of Carter Bank & Trust), `scott.riggsbee@elliott.example` (Elliott & Company's Client Services Director, who assigns orders), `coordinator@getrdone.local`, `reviewer@getrdone.local`, `admin@getrdone.local` (Avery Admin, the tenant admin; all in tenant `elliott`), `mike@millervaluation.example` (Mike Miller of Miller Valuation Group, the vendor Elliott & Company assigns orders to; tenant `elliott`), and `vendor@getrdone.local` (no tenant). The AMC staff users have fixed IDs matching the user directory; if your local Identity database seeded the coordinator and reviewer before their IDs were fixed, delete the SQL Server data volume so they are re-seeded. The automations' service accounts (such as `order-number-assigner@`, `new-order-notifier@` and `vendor-assignment-notifier@elliott.example`) are seeded with no password, so nobody can sign in as them. If your local Identity database was seeded before the tenant became `elliott`, delete the SQL Server data volume so the users are re-seeded. Vendors can also self-register from the sign-in page; confirmation and password-reset emails appear in Mailpit.

## Projects

- `GetRDone.AppHost` - Aspire: Azurite (Orleans clustering, and the `order-documents` blob container for supporting document files), KurrentDB, SQL Server (Identity, persistent volume), Mailpit, Identity, Silo, Subscriptions Worker, Web.
- `GetRDone.ServiceDefaults` - OpenTelemetry, health checks, service discovery.
- `GetRDone.Identity` - Duende IdentityServer with ASP.NET Core Identity on SQL Server and the Duende Razor Pages UI (`role`, `tenant_id` claims).
- `GetRDone.Email` - the app's `IEmailSender`, which sends over SMTP to Mailpit locally (the `mailpit` connection string); Identity's account emails and the Silo's notifications use it.
- `GetRDone.Silo` - Orleans silo; multi-tenant KurrentDB event log; KurrentDB stream providers for projections, order reactions and notifications; ManagedCode.Orleans.Identity authorization; tenant isolation of grain calls.
- `GetRDone.Web` - Blazor Server; OIDC sign-in; forwards the circuit user to grains via an outgoing grain-call filter. A client user's Home has My drafts and My orders sections (paged lists). My drafts loads from the ClientOrderDrafts projection, and My orders from the ClientOrders projection. The AMC staff's Home has the staff dashboard (Unassigned, In progress and Shipped lists), and each order opens the staff order page (`/staff/orders/{orderGuid}`). A vendor user's Home lists the orders assigned to their vendor, and each opens the vendor order page (`/vendor/orders/{orderGuid}`).
- `GetRDone.Subscriptions.Worker` - hosts the self-hosted KurrentDB catch-up subscriptions of automations that work in batches (one folder per feature) and calls the silo's grains as an Orleans cluster client. It runs as exactly one instance (`WithReplicas(1)`), since a catch-up subscription doesn't share its work with other instances. Its health check reports the subscriptions' state. `appsettings.json` lists every subscription under `Continuum:KurrentDB:Subscriptions:{Name}`; set `Enabled` to `false` to stop one without a code change (it keeps its checkpoint and catches up when turned back on).
- `Features/<Domain>/GetRDone.<Domain>.Abstractions` / `.Grains` / `.Automations` - feature slices. `.Automations` holds the logic of the domain's automations, which the worker runs; like any client it references only `.Abstractions`. `Hello` is temporary and proves the round trip (the Hello page, `/hello`).

## Starting an order draft

The caller generates a new non-empty order GUID and calls `IOrderGrain` using that GUID as the tenant-qualified grain key (for example, `client.ForTenant(tenantId).GetGrain<IOrderGrain>(orderId.ToString())`). `StartOrderDraftAsync` returns the saved changes and stream version after persisting `OrderDraftStarted`. The event time is supplied by the backend, and `InitiatedBy` is the tenant-qualified user ID (`{tenantId}|{userGuid}`) built from the authenticated identity's GUID.

IDs (order, user, client, service request type, form type, intended use) are tenant-qualified strings validated by `TenantKeyValueObject` types; an ID from another tenant is rejected. The command carries the selected IDs, versions, and names, and only current versions are accepted.

The lookups come from pre-populated read models, seeded on activation when their state is empty (the event model's seed data chapter shows them being seeded by events this model does not produce). The seed data comes from the registered `IReadModelSeedData`: the silo registers `SampleSeedData`, and the tests register their own data. The read models are stored in memory per tenant, only the `elliott` tenant is seeded, and they are recreated after a silo restart. Each tenant has one instance of each read model grain, keyed `{tenantId}|default`; use the `GetIntendedUsesGrain`, `GetDocumentTypesGrain`, `GetOrderableServicesGrain`, `GetUserDirectoryGrain` and `GetAssignableVendorsGrain` grain factory extensions to reach them with just the tenant ID:

- `IIntendedUsesGrain` (grain type `intendedUses`): Refinance, Purchase, Construction, Other. `IsCurrentIntendedUseAsync` checks the selected ID, version, and name.
- `IDocumentTypesGrain` (grain type `documentTypes`): the types a supporting document can have: Lease agreements, Rent roll, Operating statements, Other. `IsCurrentDocumentTypeAsync` checks the selected ID, version, and name.
- `IOrderableServicesGrain` (grain type `orderableServices`): the service request types, each with the form types that can be ordered with it (the user picks a service request type, then one of its form types). Appraisal Commercial has Market Value Interior Inspection and Market Value Exterior Inspection; Appraisal Residential has Uniform Residential Appraisal Report (1004) and Exterior-Only Inspection (2055). `IsCurrentOrderableServiceAsync` checks the selected service and form IDs, versions, and names, and that the form belongs to the service.
- `IUserDirectoryGrain` (grain type `userDirectory`): Ana Ruiz of Carter Bank & Trust; Scott Riggsbee, the coordinator, the reviewer and Avery Admin of Elliott & Company; Mike Miller of Miller Valuation Group (a vendor user, with the vendor's ID in `UserDirectoryEntry.VendorId`); and the automations' service accounts (titled `UserDirectoryEntry.AutomationTitle`). `IsClientUserAsync` checks that a user belongs to a client, and `IsStaffUserAsync` that a user is one of the AMC's staff (no client, no vendor, not an automation).
- `IAssignableVendorsGrain` (grain type `assignableVendors`): the vendors the AMC assigns orders to, each with the states it is licensed in: Miller Valuation Group (VA). `IsAssignableVendorAsync` checks that a vendor is one of them.

`IOrderPermissions` decides who may act on an order. Starting a draft requires the current user to be a user of the selected client; later commands will allow the user who started the order. Real tenant and permission checks belong to a full application. There is no order-entry UI yet.

## Supporting documents

Order entry tab 3 attaches supporting documents to a draft. Files are stored in blob storage (Azurite locally), never in events: the web app generates the document ID (`{tenantId}|{guid}`), uploads the file to `SupportingDocumentStorage.BlobPath` (`{tenantId}/{orderGuid}/{documentGuid}` in the `order-documents` container), and then calls `AttachSupportingDocumentAsync` with the file's name, content type, and size. `SupportingDocumentAttached` records the blob path. Files can be up to 100 MB, of any type. The upload never overwrites an existing blob. When the order rejects the document (a failed `Result`), the web app deletes the upload as a best effort; when the call throws, it keeps the file, since the order may have attached it. Removing a document (the delete button on tab 3, after a confirmation) calls `RemoveSupportingDocumentAsync`; `SupportingDocumentRemoved` records the blob path the document was attached with, and the web app deletes that file as a best effort once the removal succeeded. A failed or throwing removal keeps the file. Downloading a document's file comes with a later slice.

## Submitting an order

Order entry tab 4 (Review & Submit) shows everything saved on the draft and calls `SubmitOrderAsync`, which records `OrderSubmitted` with the draft's client. The draft needs a borrower (tab 2); supporting documents are optional, and the tab opens only once the borrower is saved. A submitted order can't be submitted again or changed with the draft commands (`FailedPrecondition`), and `GetOrderDraftAsync` rejects it, since it is no longer a draft. After submitting, the web app goes back to Home, where the draft has moved from My drafts to My orders. The order shows its number as Pending until it is assigned one (see Order numbers).

## Order numbers

Each tenant numbers its submitted orders one after another, starting at 610696, in two steps that both run as the `OrderNumberAssigner` service account (`AutomationUser`):

1. **Order Number Issuer** runs on a self-hosted KurrentDB catch-up subscription in `GetRDone.Subscriptions.Worker` (`Orders\OrderNumberIssuerSubscription`, prefix `order-`), which reads `$all` in batches and calls the silo as a cluster client; its logic is in `GetRDone.Orders.Automations`. For the `OrderSubmitted` events of a batch, it asks each tenant's `IOrderNumberGeneratorGrain` (grain type `orderNumberGenerator`, keyed `{tenantId}|default`; `GetOrderNumberGeneratorGrain(tenantId)`) to issue numbers with `IssueOrderNumbersAsync`, which records one `OrderNumberIssued` per order in a single transaction. Each event also names its order's grain as an event-scoped stream target (`OrderNumberGeneratorGrain.GetStreamTargets`), so the `order-{orderId}` stream gets only that order's event, not the rest of the batch. The generator issues an order only one number: asking again returns the number already issued and records nothing. The generator is marked `[LoadMostRecentEventsOnly(1000)]`, so its activation reads only its last 1000 events and its state keeps only those events' orders; an order asked for again after that would be issued a new number, which the order ignores.
2. **The order assigns itself its number.** The Silo's `OrderReactors` KurrentDB stream provider runs a catch-up subscription on `$all` filtered to the `orderNumberGenerator-` prefix and delivers each `OrderNumberIssued` to its order's stream, on the `OrderReactors:order` namespace keyed by the order ID. The Order grain subscribes to that namespace implicitly and reacts by signing in as `OrderNumberAssigner` and calling its own `AssignOrderNumberAsync`, which records `OrderNumberAssigned` with the order's client. An order that already has its number succeeds without changes, so an event delivered again is harmless.

Only the `OrderNumberAssigner` account may issue or assign numbers (`IOrderPermissions`). Numbers are required, so an order is skipped only when it can never take a number: its ID is invalid, or it doesn't exist or isn't submitted (gRPC `InvalidArgument`, `OutOfRange`, `NotFound`, `FailedPrecondition` or `AlreadyExists`; `AutomationErrors.IsRetryable`). Numbers are never reserved, so a number issued to such an order leaves a gap. When one order of a tenant's batch can never be issued a number, the issuer issues the others one at a time so only that order is skipped. Every other failure (an exception, a storage or silo outage, a bug, a missing permission) is retried: the issuer retries the batch with the same numbers and the worker doesn't move its checkpoint past it until no order is waiting; the order's reaction throws `OrderNumberNotAssignedException`, so the stream provider delivers the event again until it succeeds and never moves its checkpoint past it. The ClientOrders projection shows the number once `OrderNumberAssigned` arrives.

The order's reaction has its own stream provider, rather than sharing `OrderProjections`, because it runs a command: it must never run again for an event it already handled. `OrderReactors` keeps a durable checkpoint in KurrentDB (`AddKurrentDBCheckpointStore`) and starts from now on its first run, so rebuilding the projections from the start of `$all` never replays it. The worker's subscription keeps its checkpoint in KurrentDB too, since what it produces is stored there.

## New order notice

Once an order has its number, the **New Order Notifier** emails the AMC staff member who assigns orders, the tenant's user titled Client Services Director in the user directory (`UserDirectoryEntry.ClientServicesDirectorTitle`; Scott Riggsbee in `elliott`), and records `NewOrderNoticeSent` on the order with the recipient and subject. The email appears in Mailpit.

The Silo's `NotificationReactors` KurrentDB stream provider runs a catch-up subscription on `$all` filtered to the `order-` prefix and delivers each order's events on the `NotificationReactors:order` namespace keyed by the order ID. `NewOrderNotifierGrain` (grain type `newOrderNotifier`, in `GetRDone.Orders.Grains`) subscribes to it implicitly, so each order has its own notifier, separate from the order grain so sending an email never holds up the order. On `OrderNumberAssigned` it signs in as the `NewOrderNotifier` service account, finds the recipient and the client's name in the user directory, asks the order whether the notice was already sent (`IsNewOrderNoticeSentAsync`), sends the email, and records it with `SendNewOrderNoticeAsync`. Only the `NewOrderNotifier` account may record or ask about the notice. Recording it again succeeds without changes; an order without a number is rejected (`FailedPrecondition`).

An event delivered again (for example, after a silo restart before the checkpoint is saved) doesn't email again, since the notifier checks first. An email that went out just before the notifier failed to record it is sent again when the event is redelivered; the sample accepts that rare duplicate rather than missing a notice. An email that can't be sent, or a notice that wasn't recorded for a reason that may pass (`AutomationErrors.IsRetryable`; `NewOrderNoticeNotRecordedException`), is retried by redelivery; a tenant with no Client Services Director is logged and skipped.

Like `OrderReactors`, the provider has a durable KurrentDB checkpoint and starts from now on its first run, so notices are never sent again when the projections are rebuilt. It is a provider of its own because it reads the order streams themselves, while `OrderReactors` reads only the generator streams.

## Assigning and acknowledging orders

The AMC's staff roles are in `StaffRoles` (Abstractions; they match `GetRDoneRoles`): `amc-coordinator`, `amc-reviewer`, `amc-client-services-director` and `tenant-admin`. A submitted order goes through these statuses:

- **Submitted.** Only the Client Services Director or the tenant admin can assign an order (`AssignOrderAsync` with the assignee's tenant user ID; `OrderAssigned`), and only to one of the AMC's staff in the user directory (otherwise `InvalidArgument`). An order that is a draft or already assigned is rejected (`FailedPrecondition`). The staff order page offers **Assign to me**.
- **Assigned.** Only the assignee can acknowledge the order (`AcknowledgeOrderAsync`; `OrderAcknowledged`), which says they are working on it. The staff order page offers **Acknowledge**.
- **Acknowledged.** The assignee, or anyone who may assign orders, can ask the client for a document (see Document requests) and submit the description of work for approval (see Description of work). The staff order page offers **Request a document** and **Write the description of work**.
- **Description of work awaiting approval.** The description of work can be revised until the client approves it.
- **Description of work approved.** Documents can still be requested, and the assignee, the Client Services Director or the tenant admin can assign the order to a vendor (see Assigning a vendor). The staff order page offers **Assign a vendor**.
- **Vendor assigned.** Documents can still be requested. The vendor schedules the inspection (see Inspection and report).
- **Inspection scheduled** and **Inspection completed.** The vendor's progress; documents can still be requested.
- **Report delivered.** Documents can still be requested, and the assignee, the Client Services Director or the tenant admin can ship the order (see Shipping). The staff order page offers **Mark shipped**.
- **Shipped.** The order is complete; nothing more can be done but take its number.

An order can take its number in any status after Submitted, since the number may arrive after the order is assigned.

## Document requests

Once an order is acknowledged, the assignee, the Client Services Director or the tenant admin can ask the client who started the order for a document of one of the tenant's document types, with a message (`RequestClientDocumentAsync`; `ClientDocumentRequested`). The staff order page generates the request ID (`{tenantId}|{guid}`); the request goes to the order's `StartedBy` and carries the order's number, when it has one. A request ID used before is rejected (`AlreadyExists`), as is an order that is not acknowledged yet (`FailedPrecondition`). An order can have several open requests at once.

The **Document Request Notifier** (`DocumentRequestNotifierGrain`, grain type `documentRequestNotifier`, on the same `NotificationReactors` provider as the New Order Notifier) emails the client, signed in as the `DocumentRequestNotifier` service account, with a link to the client order page, and records `DocumentRequestNoticeSent` on the request with `SendDocumentRequestNoticeAsync`. It asks the order first (`IsDocumentRequestNoticeSentAsync`), so a redelivered request isn't emailed twice, and recording a notice again succeeds without changes. The link uses `NotificationOptions.WebBaseUrl`, which the AppHost sets from the web app's https endpoint (`WEB_BASE_URL`); without it the email has no link.

The client sees the open requests on the client order page (`/orders/{orderGuid}`, opened from My orders) and uploads each one there. Like tab 3 of order entry, the web app uploads the file to `SupportingDocumentStorage.BlobPath` first and then calls `ProvideRequestedDocumentAsync` (`RequestedDocumentProvided`), which adds the document to the order's supporting documents as the requested type. Only the client the document was requested from can provide it, once per request (`FailedPrecondition` after that); the notice doesn't need to be sent first.

Both order pages list the order's documents, each linking to `GET /orders/{orderGuid}/documents/{documentGuid}` (`OrderDocumentDownloads`, mapped in the web app). The endpoint asks the read model for the user's role, `OrderDetails` for staff, `ClientOrderDetails` for clients and `VendorOrderDetails` for vendor users, so staff can download the documents and report of their tenant's orders, a client the documents and shipped report of the orders they started and a vendor's users the report they delivered; anything else gets the read model's error status, or `404` when the order has no such document. Orleans Identity copies the user into the Orleans request context only for MVC actions and SignalR hubs (Blazor), so the endpoint sets it itself. The file is always sent as an attachment with `X-Content-Type-Options: nosniff` and `Cache-Control: private, no-store`, so an uploaded HTML or SVG file never runs in the app's origin. Documents of drafts can't be downloaded, since both read models return `NotFound` for drafts.

## Description of work

Once an order is acknowledged, the assignee, the Client Services Director or the tenant admin writes the description of work in a rich text editor on the staff order page and submits it for the approval of the client who started the order (`SubmitDescriptionOfWorkAsync`; `DescriptionOfWorkSubmitted`). The approver is always the order's `StartedBy`. The page generates the ID (`{tenantId}|{guid}`) of version 1; each revision keeps the ID and is one version more than the version it revises, so a revision based on an outdated version is rejected (`Aborted`). Revisions are allowed until the client approves; after that a submission is rejected (`FailedPrecondition`), as is an order that is not acknowledged yet.

The editor is [Tizzani.MudBlazor.HtmlEditor](https://github.com/erinnmclaughlin/MudBlazor.HtmlEditor), which wraps [Quill](https://quilljs.com/) (loaded from jsDelivr with an SRI hash in `App.razor`). The description of work is stored as HTML: `DescriptionOfWorkHtml` sanitizes it with [HtmlSanitizer](https://github.com/mganss/HtmlSanitizer) when it is submitted (images are removed; an editor with no text is rejected), and both order pages sanitize it again before showing it with `MudHtmlViewer`, so markup is never trusted as stored.

The client sees the description of work on the client order page and approves the version shown (`ApproveDescriptionOfWorkAsync`; `DescriptionOfWorkApproved`), after a confirmation. Only the order's `StartedBy` can approve, and only the version that waits for approval (`FailedPrecondition` for a version revised since the page loaded, or one already approved).

Two notifiers on the `NotificationReactors` provider send the emails, each signed in as its own service account:

- The **Description of Work Approval Notifier** (`DescriptionOfWorkApprovalNotifierGrain`, grain type `descriptionOfWorkApprovalNotifier`) emails the client a link to the client order page for each version submitted, saying when it is a revision, and records `DescriptionOfWorkSubmittedNoticeSent` with `SendDescriptionOfWorkSubmittedNoticeAsync`. It asks the order first (`IsDescriptionOfWorkSubmittedNoticeDueAsync`), so it doesn't email a version again when the event is delivered again, nor a version that was revised or approved since.
- The **Description of Work Approved Notifier** (`DescriptionOfWorkApprovedNotifierGrain`, grain type `descriptionOfWorkApprovedNotifier`) emails the assignee a link to the staff order page when the client approves, and records `DescriptionOfWorkApprovedNoticeSent` with `SendDescriptionOfWorkApprovedNoticeAsync`, after asking `IsDescriptionOfWorkApprovedNoticeSentAsync`.

Documents can still be requested while the description of work waits for approval and after it is approved, and the order can still take its number.

## Assigning a vendor

Once the client approves the description of work, the assignee, the Client Services Director or the tenant admin assigns the order to one of the tenant's vendors (`IAssignableVendorsGrain`) on the staff order page, with the vendor's fee and due date and the client's service fee and due date (`AssignVendorAsync`; `VendorAssigned`). The client doesn't enter a due date when ordering; it is set here. Both fees are between $0.01 and $999,999.99 with at most two decimals, the vendor's due date can't be in the past and the client's due date can't be before the vendor's (`InvalidArgument`), nor can a vendor that isn't one of the tenant's be assigned. The staff order page fills in the client's due date as the vendor's plus three days, to leave time for review and revisions, and staff can change it. The event carries the approved description of work's ID and version and the order's number, when it has one. An order is assigned to a vendor once: an order whose description of work isn't approved, or that already has a vendor, is rejected (`FailedPrecondition`).

The **Vendor Assignment Notifier** (`VendorAssignmentNotifierGrain`, grain type `vendorAssignmentNotifier`, on the `NotificationReactors` provider) emails each of the vendor's users in the user directory (`UserDirectoryEntry.VendorId`) a link to the vendor order page, signed in as the `VendorAssignmentNotifier` service account, then records `VendorAssignedNoticeSent` once with all the recipients (`SendVendorAssignedNoticeAsync`). It asks the order first (`IsVendorAssignedNoticeSentAsync`), and the order accepts only recipients who are users of the vendor the order is assigned to (`InvalidArgument`).

Vendor users see their vendor's orders on their Home and open each on the vendor order page, with the client, the property, the access contact, the fee and due date, the approved description of work and a timeline that starts at the assignment. Vendor access comes from the user directory's `VendorId`, not the `vendor` role: a vendor user can only see their own vendor's orders (`PermissionDenied`), and Val Vendor, who has no tenant, sees none. Vendors never see the client's service fee or due date. The client sees only that an appraiser was assigned, not who, along with the service fee and due date.

## Inspection and report

Only the users of the vendor the order is assigned to (`UserDirectoryEntry.VendorId`) can do the vendor's work (`PermissionDenied` for anyone else, `FailedPrecondition` before a vendor is assigned), each step once and in order on the vendor order page:

1. **Schedule the inspection** (`ScheduleInspectionAsync`; `InspectionScheduled`) with its date and time and who the vendor meets, filled in with the access contact. The time can't be in the past (`InvalidArgument`). The page picks the time in the web server's time zone, the one it shows times in.
2. **Complete the inspection** (`CompleteInspectionAsync`; `InspectionCompleted`) with the date it was completed, which can't be in the future (`InvalidArgument`).
3. **Deliver the report** (`DeliverReportAsync`; `ReportDelivered`). Like the client's uploads, the web app uploads the file to `SupportingDocumentStorage.BlobPath` first, so the report is stored with the order's other documents, and deletes it again when the order rejects it. The report is not a supporting document: it is the order's own `Report`, not in its document list. A document ID the order already has is rejected (`AlreadyExists`).

A step done out of order or again is rejected (`FailedPrecondition`); the inspection can't be rescheduled yet. The client sees the inspection's progress in the order's status and timeline, but not the date or the report, which it gets when the order ships.

The **Report Delivered Notifier** (`ReportDeliveredNotifierGrain`, grain type `reportDeliveredNotifier`, on the `NotificationReactors` provider) emails the staff member the order is assigned to a link to the staff order page, signed in as the `ReportDeliveredNotifier` service account, and records `ReportDeliveredNoticeSent` with `SendReportDeliveredNoticeAsync`, after asking `IsReportDeliveredNoticeSentAsync`. The order accepts only the assignee as the recipient (`InvalidArgument`).

## Shipping

Once the vendor delivers the report, the assignee, the Client Services Director or the tenant admin ships it to the client (`ShipOrderAsync` with the report's document ID; `OrderShipped`), which completes the order. The staff order page offers **Mark shipped** and asks to confirm the report, the order number and the client first, since shipping can't be undone. An order whose report isn't delivered, or that already shipped, is rejected (`FailedPrecondition`), as is a document that isn't the delivered report (`NotFound`). The event carries the client user who entered the order (`EnteredByUserId`) and the order's number, when it has one; it is when the order shipped (`OccurredAt`). There are no revisions after shipping.

The report is stored with the order's other documents, as delivered. The client sees it on the client order page only once the order ships, with a link to download it (`ClientOrderDetails.Report`), and the order's status and timeline show it shipped. The vendor's part ends at the delivered report, so the vendor's projections ignore `OrderShipped`.

The **Order Shipped Notifier** (`OrderShippedNotifierGrain`, grain type `orderShippedNotifier`, on the `NotificationReactors` provider) emails the client who entered the order a link to the client order page, signed in as the `OrderShippedNotifier` service account, and records `OrderShippedNoticeSent` with `SendOrderShippedNoticeAsync`, after asking `IsOrderShippedNoticeSentAsync`. The order accepts only the client who entered it as the recipient (`InvalidArgument`).

Every order event also targets the per-user stream `clientUserOrders-{tenantId}|{userGuid}` of the user who started the order (`OrderGrain.GetStreamTargets`, transaction-scoped so the stream gets every event of the order's transaction), so one projection can group all of a user's orders. The Silo's `OrderProjections` KurrentDB stream provider runs a catch-up subscription on `$all` filtered to the `order-` stream prefix and delivers each event to its order stream and its target streams. Projection grains implicitly subscribe to the `OrderProjections:clientUserOrders` namespace, so Orleans activates one grain per user, keyed by the user's tenant user ID.

- `IClientOrderDraftsGrain` (grain type `clientOrderDrafts`; `GetClientOrderDraftsGrain(tenantUserId)`): the user's drafts that are not submitted yet, most recently saved first (`OrderSubmitted` removes a draft). `GetDraftsAsync(skip, take)` returns one page and the total count. Only the user can read their own drafts.
- `IClientOrdersGrain` (grain type `clientOrders`; `GetClientOrdersGrain(tenantUserId)`): the user's submitted orders, most recently submitted first, each with its property address, form type, order number (null until one is assigned) and status (`ClientOrderStatus`: `Submitted`, `Assigned`, `Acknowledged`, `DescriptionOfWorkAwaitingApproval`, `DescriptionOfWorkApproved`, `VendorAssigned`, `InspectionScheduled`, `InspectionCompleted` or `Shipped`; a delivered report shows as `InspectionCompleted` until the order ships). It keeps the address and form type of the user's drafts from `OrderDraftStarted` and `RequestAndPropertySaved`, since `OrderSubmitted` carries neither, and `OrderSubmitted` turns the draft into an order. `GetOrdersAsync(skip, take)` returns one page and the total count. Only the user can read their own orders.
- `IClientOrderDetailsGrain` (grain type `clientOrderDetails`; `GetClientOrderDetailsGrain(orderId)`): the client order page of one submitted order (drafts are `NotFound`), projected from the order's own stream on `OrderProjections:order`. It shows the order's status, assignee, service fee and due date (once a vendor is assigned), open document requests, supporting documents, description of work, the report once the order ships, and timeline, and whether the client can upload a requested document or approve the description of work (`ClientOrderActions`). Only the user who started the order can read it.

## Staff order projections

Every order event also targets the per-tenant stream `tenantOrders-{tenantId}|default` (`OrderProjections.TenantOrdersStreamTarget`, transaction-scoped), and the provider delivers each order's own stream on the `OrderProjections:order` namespace keyed by the order ID. Only the AMC's staff (any `StaffRoles` role) can read these projections. They store user and client IDs and turn them into names from the tenant's user directory when they are read, so names are always current.

- `IUnassignedOrdersGrain` (grain type `unassignedOrders`; `GetUnassignedOrdersGrain(tenantId)`): the dashboard's Unassigned list, the orders that have their number and are not assigned, oldest (lowest order number) first. `OrderNumberAssigned` puts an order on the list and `OrderAssigned` takes it off; an order assigned before it has its number never appears. It keeps what the list shows of each order from `OrderDraftStarted` and `RequestAndPropertySaved`.
- `IInProgressOrdersGrain` (grain type `inProgressOrders`; `GetInProgressOrdersGrain(tenantId)`): the dashboard's In progress list, the assigned orders with their assignee, status (`StaffOrderStatus`) and due date, due first first, then the orders without a due date yet (it is set by `VendorAssigned`) by order number. `OrderAssigned` puts an order on the list and `OrderShipped` takes it off.
- `IShippedOrdersGrain` (grain type `shippedOrders`; `GetShippedOrdersGrain(tenantId)`): the dashboard's Shipped list, the shipped orders with when they shipped, most recently shipped first. `OrderShipped` puts an order on the list. It keeps what the list shows of each order from `OrderDraftStarted`, `RequestAndPropertySaved` and `OrderNumberAssigned` until then.
- `IOrderDetailsGrain` (grain type `orderDetails`; `GetOrderDetailsGrain(orderId)`): the staff order page of one submitted order (drafts are `NotFound`), with a timeline of what happened to it, most recent first, the document requests the client hasn't provided yet, the order's documents with who added them and when (attached, removed and provided), the latest version of the description of work, the vendor the order is assigned to with its fee and due date, the client's service fee and due date, the inspection and the delivered report, and the actions the current user may take (`OrderActions`).

## Vendor order projections

Only users with a `VendorId` in the user directory can read these projections, and only their own vendor's orders.

- `IVendorOrdersGrain` (grain type `vendorOrders`; `GetVendorOrdersGrain(tenantId)`): the vendor dashboard's Orders list, projected from the tenant's orders stream. `VendorAssigned` puts an order on the list; the query returns only the signed-in user's vendor's orders, due first first.
- `IVendorOrderDetailsGrain` (grain type `vendorOrderDetails`; `GetVendorOrderDetailsGrain(orderId)`): the vendor order page of one order, projected from the order's own stream; `NotFound` until the order is assigned to a vendor. It shows the inspection and the delivered report, and the vendor's next step (`VendorOrderActions`).

The checkpoint and the projections are stored in memory, so after a silo restart the subscription replays from the start and rebuilds them.

## Tenant isolation

Grain keys are tenant-qualified (`{TenantId}|{Key}`), and the silo keeps every call inside one tenant. `AddTenantIsolation()` in GetRDone.Silo sets this up for every feature's grains, and GetRDone.Silo.Tests tests it:

- Calls from cluster clients (GetRDone.Web and GetRDone.Subscriptions.Worker): `ClientCallTenantFilter` requires a signed-in user whose `tenant_id` claim is the tenant of the grain being called, and throws `UnauthorizedAccessException` otherwise. This also covers grains without `[Authorize]`. The worker's automation accounts sign in for one tenant at a time, so they pass the same check.
- Calls from grains: Orleans.Multitenant's `AddMultitenantCommunicationSeparation()` rejects a call into another tenant. It does not check client calls, which is why the filter above is needed. No cross-tenant access is authorized.

Calls to grains whose key has no tenant (such as the stream checkpoint grains) and to `Orleans.*` interfaces are not checked. Within a tenant, the grains still check the user's roles and, for client and vendor users, which orders they can see.
